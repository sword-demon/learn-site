# Feature Specification: 运营异常收件箱

**Feature Branch**: `[014-ops-exception-inbox]`

**Created**: 2026-09-05

**Status**: Draft

**Input**: User description: "把未发布课程、异常学习地图、待答问题、待处理反馈、支付未知状态、队列失败和长期未处理的运营异常汇成按权限和数据范围裁剪的行动列表，每项直接跳到处理位置并显示积压年龄、影响范围和建议动作。可恢复的通知任务先自动有限重试，只有超过阈值才进入人工收件箱。

现有能力很多，但'知道哪里有事'与'完成处理'之间仍靠人工跳转；异常收件箱能把个人运营者的注意力集中到正在造成损失的事项。需要统一待办状态和排序规则；数据范围过滤必须沿用现有权限模型；所有异常都塞入时会退化成噪音列表。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 单点看到全部待处理异常 (Priority: P1)

作为后台运营人员 (普通员工 / 管理员 / 超级管理员), 登录管理端后打开"异常收件箱"页面, 在一个统一列表中看到所有需要我处理的事项, 每条都直接显示"积压多久 / 影响范围 / 建议动作 / 跳转入口", 点击跳转直接进入对应的处理页面 (例如未发布课程、待答问题、待处理反馈、异常学习地图、支付未知订单、队列失败任务、长期未处理运营异常)。

**Why this priority**: 这是本次功能的核心交付 - 解决"知道哪里有事"与"完成处理"之间靠人工跳转的问题; 没有这一步, 后续的过滤、排序、重试都失去意义。

**Independent Test**: 用至少一个真实异常 (例如一条未发布课程 + 一条队列失败) 触发收件箱渲染, 验证: 列表出现, 每条显示积压年龄 (例如"已 3 天")、影响范围 (例如"3 个学员")、建议动作 (例如"审核发布")、可点击跳转到对应页面; 跳转后页面正常加载。

**Acceptance Scenarios**:

1. **Given** 当前账号是普通运营, **When** 打开收件箱, **Then** 看到与自己数据范围相关的全部异常 (例如: 涉及的课程、订单、学员), 且不显示他人数据范围内的异常。
2. **Given** 收件箱有 1 条未发布课程 (积压 2 天) + 1 条队列失败任务, **When** 渲染, **Then** 两条都按统一状态字段呈现 (open / retrying / snoozed / resolved), 且列表项包含跳转按钮。
3. **Given** 用户点击列表项的"跳转到处理", **When** 点击, **Then** 跳转到对应业务模块的处理页 (课程列表 / 订单详情 / 问答详情 / 反馈详情等), URL 与现有模块路由一致, 不破坏现有跳转路径。

---

### User Story 2 - 统一排序规则抑制噪音 (Priority: P1)

作为后台运营人员, 在收件箱内看到的列表是按"业务影响 + 积压年龄"统一排序的, 而不是按异常类型分块展示 - 这样真正在造成损失 (例如支付未知) 的事项不会被淹没在大量低风险提醒中。

**Why this priority**: "所有异常都塞入时会退化成噪音列表"是用户明确警告的反模式; 没有排序规则, P1 故事也无法发挥价值。

**Independent Test**: 构造 1 条支付未知 (积压 1 小时) + 10 条未发布课程 (积压 30 天) + 1 条队列失败 (积压 6 小时), 验证列表顶部是"支付未知", 而非按异常类型聚集展示。

**Acceptance Scenarios**:

1. **Given** 收件箱有多种异常类型混合, **When** 加载页面, **Then** 列表按"业务影响权重 × 积压时长"统一排序, 顶部是影响最大或积压最久的事项。
2. **Given** 收件箱空 (当前账号无待处理异常), **When** 打开, **Then** 展示"暂无待处理事项"的空态, 而不是空列表或错误。
3. **Given** 异常总数超过阈值 (例如 200 条), **When** 加载, **Then** 按排序分页或按类型折叠, 不一次性渲染全部; 每页顶部展示"已加载 X / 共 Y 条"。

---

### User Story 3 - 可恢复通知任务自动有限重试 (Priority: P2)

作为系统 (自动化), 对于"可恢复"的发送任务 (短信 / 推送 / 队列通知), 在进入人工收件箱之前先自动重试有限次数 (例如最多 3 次), 只有当重试用尽或属于"不可恢复"类型 (例如参数错误、账户被禁) 时, 才进入人工收件箱。

**Why this priority**: 这是用户明确要求的减噪机制 - 把可以自我恢复的事项挡在人工视野外, 避免收件箱被瞬时失败淹没; 它依赖 P1 故事存在, 但本身可独立测试。

**Independent Test**: 注入 1 条短信发送任务, 首次失败 (模拟网络抖动), 验证: 任务进入"自动重试"状态 (不进入人工收件箱), 重试 2 次后第三次成功, 状态变为"已发送", 收件箱不出现此条; 另注入 1 条账户被禁的推送任务, 验证: 立刻标记为"不可恢复", 直接进入收件箱, 附带"建议动作: 检查账户状态"。

**Acceptance Scenarios**:

1. **Given** 一条通知任务因瞬时错误失败 (例如 HTTP 502), **When** 第一次失败, **Then** 任务进入 retrying 状态, 不进入收件箱, 最多重试 N 次 (默认 3, 可配置), 退避策略为指数。
2. **Given** 一条通知任务重试 N 次仍失败, **When** 达到阈值, **Then** 任务进入人工收件箱 (open 状态), 标记为"自动重试已耗尽", 建议动作显示"手动重发或转人工"。
3. **Given** 一条通知任务首次失败原因为"账户被禁 / 参数非法"等明确不可恢复类型, **When** 失败, **Then** 跳过自动重试, 直接进入人工收件箱, 建议动作针对具体错误码给出。

---

### User Story 4 - 数据范围过滤沿用现有权限模型 (Priority: P1)

作为不同权限等级的后台账号 (普通员工 / 管理员 / 超级管理员), 看到的异常是按现有权限模型裁剪过的: 普通员工只看自己数据范围, 管理员看更大范围, 超级管理员看全部。

**Why this priority**: "数据范围过滤必须沿用现有权限模型"是用户明确硬要求; 如果权限过滤出错, 会泄漏其他账号的学员数据, 这既是安全问题也是合规问题。

**Independent Test**: 用一个普通员工账号登录, 注入 2 条异常 - 1 条属于该员工负责范围, 1 条属于其他员工范围, 验证: 只看到 1 条; 用超级管理员账号登录, 看到全部。

**Acceptance Scenarios**:

1. **Given** 普通员工 A 与普通员工 B 分别负责不同课程 / 学员集合, **When** A 打开收件箱, **Then** 看到的异常只涉及 A 负责的范围, 不涉及 B。
2. **Given** 管理员 C, **When** 打开收件箱, **Then** 看到 C 管辖范围内的全部异常, 包含下属员工尚未处理的。
3. **Given** 超级管理员 D, **When** 打开收件箱, **Then** 看到所有异常, 含跨管辖范围的。
4. **Given** 任何账号尝试通过 URL 直接访问不属于自己范围的异常详情, **When** 后端鉴权, **Then** 返回 403, 拒绝读取。

---

### User Story 5 - 待办状态可推进 (Priority: P2)

作为后台运营人员, 在收件箱里可以将异常标记为"已处理" / "暂时搁置" / "已指派给某人", 并且这些状态变更可被审计。

**Why this priority**: 这是用户隐含的"行动列表"含义 - 列表不仅是显示, 还必须能推进; 但它可以晚于 P1 故事交付, 不阻塞核心减噪价值。

**Independent Test**: 在收件箱列表里点选 1 条异常, 标记"已处理", 验证: 列表立即移除该条, 写入 audit_log, 刷新页面后该条不再出现; 标记"暂时搁置", 验证: 该条暂时隐藏但可从"已搁置"过滤标签找回。

**Acceptance Scenarios**:

1. **Given** 收件箱有 1 条 open 状态异常, **When** 点击"标记为已处理", **Then** 该条从默认视图移除, 状态变为 resolved, audit_log 写入一条状态变更记录。
2. **Given** 收件箱有 1 条 open 状态异常, **When** 点击"搁置到明天", **Then** 该条从默认视图移除, 状态变为 snoozed, 直到设定时间才再次出现。
3. **Given** 收件箱有 1 条 open 状态异常, **When** 点击"指派给 X", **Then** 该条从我的视图移除 (若指派给其他人), 出现在被指派人的收件箱, audit_log 写入指派动作。

---

### Edge Cases

- 收件箱首次上线时, 历史未处理的运营异常如何处理? 假设: 一次性数据迁移把所有 open 状态的异常纳入; 数据迁移失败时回滚且不阻塞收件箱加载。
- 同一异常来源 (例如同一条订单) 多次进入失败队列时, 收件箱如何去重? 假设: 按"异常源 + 异常类型"去重, 同一源同一类型只显示最新一条, 点击展开看历史。
- 自动重试与人工收件箱的边界条件: 任务在重试中被管理员手动"标记已处理"了, 自动重试的下一轮如何处理? 假设: 手动标记后, 自动重试任务取消, 不再推送。
- 权限变更 (员工被调整负责范围) 后, 已存在的异常是否还对他可见? 假设: 异常在创建时打快照"当前可见人集合", 后续权限变更不影响历史归属, 但未来新增异常按新规则。
- 收件箱页面加载时, 后端聚合 7 个异常来源耗时过长? 假设: 后端按"先列清单 + 后聚合详情"两阶段返回, 前端首屏 < 1.5s 可见骨架, 详情懒加载。
- 自动重试配置 (重试次数、退避) 写死还是可配置? 假设: 后端有 service 私有常量, 提供环境变量覆盖, 不暴露给运营操作界面。
- 收件箱数据是否实时刷新? 假设: 列表使用轮询 (30s) 而非 WebSocket, 避免引入新依赖; 状态变更后立即乐观更新。
- 单条异常在收件箱停留多久算"长期未处理"? 假设: 默认阈值 72 小时 (积压年龄显示"已 3 天"), 阈值可配置, 不区分异常类型但建议动作按类型定制。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 后端 MUST 提供聚合查询接口, 把以下异常来源合并为统一的"运营异常"列表: 未发布课程、异常学习地图 (学员学习卡在中间状态超过阈值)、待答问题 (超过 X 小时未回复)、待处理反馈 (用户反馈超过 Y 小时未处理)、支付未知状态订单、队列执行失败任务、长期未处理运营异常 (积压 > 72h 的所有 open 项)。
- **FR-002**: 后端 MUST 在聚合查询时按"业务影响权重 × 积压时长"统一排序, 业务影响权重按异常类型预定义 (支付未知 > 队列失败 > 待答问题 > 未发布课程 > 异常学习地图 > 待处理反馈 > 长期未处理)。
- **FR-003**: 后端 MUST 在聚合查询时沿用现有权限模型裁剪数据范围: 普通员工只看到自己负责的学员 / 课程范围内的异常, 管理员看到自己管辖范围, 超级管理员看到全部。
- **FR-004**: 后端 MUST 对每条异常计算"积压年龄"字段 (从异常产生到当前时间), 前端 MUST 按"X 分钟 / X 小时 / X 天"友好格式化。
- **FR-005**: 后端 MUST 对每条异常提供"建议动作"字段 (按异常类型 + 错误码预定义), 前端 MUST 直接渲染该字段。
- **FR-006**: 后端 MUST 对每条异常提供"跳转路径"字段 (深链到现有业务模块的具体页面, 包含必要的查询参数), 前端 MUST 提供"跳转到处理"按钮并按该路径跳转。
- **FR-007**: 后端 MUST 对每条异常提供"影响范围"字段 (例如涉及的学员数 / 订单金额 / 课程数), 前端 MUST 在列表项中渲染该字段。
- **FR-008**: 后端 MUST 实现"自动有限重试"机制: 可恢复的通知任务失败时进入 retrying 状态, 最多重试 N 次 (默认 3), 退避策略为指数 (默认 1 分钟起步); 重试耗尽或明确不可恢复才进入人工收件箱。
- **FR-009**: 后端 MUST 把"自动重试已耗尽"与"不可恢复"两类异常在收件箱中明确区分 (例如通过 type / subtype 字段), 让前端能渲染不同的建议动作。
- **FR-010**: 前端 MUST 实现收件箱页面, 显示列表 / 排序 / 空态 / 折叠, 支持"已处理 / 搁置 / 指派"三种状态推进动作。
- **FR-011**: 前端 MUST 实现"按类型 / 状态 / 积压年龄"过滤与排序的二级视图, 默认视图只显示 open 状态的异常。
- **FR-012**: 后端 MUST 把状态变更 (处理 / 搁置 / 指派) 写入 audit_log, 与现有审计规则一致 (通过 service 私有方法 `writeAudit`)。
- **FR-013**: 后端 MUST 在异常列表渲染时按"异常源 + 异常类型"去重, 同一源同一类型只显示最新一条, 详情里展示历史。
- **FR-014**: 后端 MUST 提供"搁置到期重新出现"机制: snoozed 状态的异常到达设定时间后自动重新进入 open 视图。
- **FR-015**: 后端 MUST 拒绝越权访问: 通过 URL 直接访问不属于自己范围的异常详情时, 返回 403; 前端跳转前检查权限范围避免无意义跳转。
- **FR-016**: 后端 MUST 提供服务健康检查, 异常聚合查询耗时超过阈值 (例如 1.5s) 时记日志, 必要时返回部分结果加降级提示。
- **FR-017**: 后端 MUST 为所有新增数据表 (例如异常聚合表 / 重试队列表) 编写 think-orm 迁移, 沿用现有迁移流程 (进入版本控制 + 可回滚)。
- **FR-018**: 后端 MUST 把重试配置 (次数 / 退避初始值 / 最大值) 集中到 service 私有常量, 环境变量可覆盖, 不暴露给运营操作界面。
- **FR-019**: 后端 MUST 把异常类型的预定义"业务影响权重" / "建议动作" / "跳转路径模板"集中到 service 私有常量, 跨方法复用同一份配置。
- **FR-020**: 前端 MUST 使用现有 Element Plus / Tailwind / Pinia / Vue Router 栈, 不引入新依赖; 收件箱页面 MUST 通过现有管理端路由守卫与权限组件, 不绕过鉴权。

### Key Entities *(include if feature involves data)*

- **运营异常 (OpsException)**: 异常来源 (枚举: 未发布课程 / 异常学习地图 / 待答问题 / 待处理反馈 / 支付未知 / 队列失败 / 长期未处理); 异常类型 (细分子类型, 例如支付未知下的 ZPay 回调超时); 业务主键 (源记录 ID); 积压年龄 (派生字段); 影响范围 (派生字段, JSON); 建议动作 (派生字段, 短文本); 跳转路径 (派生字段); 状态 (open / retrying / snoozed / resolved / assigned); 指派人 ID (可空); 搁置到期时间 (可空); 创建时间; 更新时间。
- **重试任务 (RetryJob)**: 关联的运营异常 ID; 重试次数上限; 已重试次数; 下次重试时间; 退避参数 (初始间隔, 最大间隔); 最后一次错误码; 最后一次错误摘要; 状态 (pending / succeeded / exhausted); 创建时间。
- **审计记录 (AuditLog)**: 沿用现有 audit_log 表; 收件箱相关的动作类型: 标记已处理 / 搁置 / 指派 / 强制重试 / 解除重试; 字段格式与现有审计一致 (actor_id / action / target / created_at)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运营人员从登录到看到自己范围内全部待处理异常的耗时 < 30 秒 (含跳转收件箱页 + 列表渲染), 显著短于"逐个模块查找"的现状 (估算 5-10 分钟)。
- **SC-002**: 收件箱列表首屏可见时间 < 1.5 秒 (含聚合查询 + 排序 + 权限裁剪), 后端聚合耗时 P95 < 800ms。
- **SC-003**: 收件箱自动重试覆盖率达 80% 以上 (即可恢复的瞬时失败中, 至少 80% 在人工收件箱出现之前已被自动恢复), 人工收件箱的"队列失败"项数量较上线前下降 ≥ 50%。
- **SC-004**: 收件箱权限裁剪 0 泄漏: 通过安全测试验证普通员工无法看到其他员工范围的异常; 越权 URL 访问 100% 返回 403。
- **SC-005**: 列表噪音控制: 同一账号同时看到的未处理异常默认视图 ≤ 50 条 (按排序 + 折叠 / 分页实现), 防止一次性渲染超长列表造成注意力退化。
- **SC-006**: 状态推进可追溯: 任意收件箱状态变更 (处理 / 搁置 / 指派) 100% 写入 audit_log, 可在审计页查到 actor / action / target / 时间。
- **SC-007**: 收件箱页面对自动重试任务提供"建议动作 = 等待自动重试"提示, 对不可恢复任务提供针对性的"建议动作 = 检查 X"提示; 通过抽样检查覆盖所有异常类型。

## Assumptions

- 现有"未发布课程 / 异常学习地图 / 待答问题 / 待处理反馈 / 支付未知 / 队列失败"模块均有"我负责的 / 我管辖的"权限裁剪点, 不需要重新定义权限模型; 收件箱聚合时复用现有裁剪函数。
- 后端聚合查询不需要写入新数据库表来"汇总"异常, 而是从各业务模块现成数据源直接派生; 只有"收件箱状态推进"和"重试任务"需要新增表 (迁移沿用现有流程)。
- 现有管理端路由 / 权限组件 / Pinia store 已支持权限范围裁剪, 收件箱页面可以直接复用; 不引入新的权限中间件。
- 自动重试使用 webman/redis-queue 现成 worker 机制, 不引入新的队列框架; 重试配置 (次数 / 退避) 通过环境变量注入, 默认值集中在 service 私有常量。
- 收件箱页面是新增页面 (路由), 不替换现有任何一个业务模块的页面; 各业务模块的处理流程不变, 收件箱只是"聚合入口"。
- 异常影响范围"学员数 / 订单金额"等数字按当前账号数据范围实时计算, 不做缓存; 单条异常聚合耗时 P95 < 50ms。
- 收件箱默认轮询间隔 30 秒; 状态变更后通过乐观更新立即反映, 不等待下一次轮询; 不引入 WebSocket 推送。
- "长期未处理"特指积压 > 72 小时且仍处于 open 状态的任何异常 (含前 6 类); 72 小时阈值可通过环境变量覆盖, 默认值集中在 service 私有常量。
- 收件箱数据源覆盖以下 7 类, 不包括登录失败审计 / 学员投诉等需要专门流程的事项 (那些继续走各自专项入口)。
- 收件箱上线时不做历史数据回填 (例如把过去 30 天积压的异常全部算入), 而是从上线当天起累计积压年龄; 上线前积压的事项不进入收件箱, 但保留各自的旧入口可见。
