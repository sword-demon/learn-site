# Research: 013-learning-action-loop

## R1：下一步接口边界

**Decision**：新增受学习端鉴权保护的 `GET /api/learner/v1/me/next-action`，不把个性化结果并入公开 `GET /home`，也不把它塞进 `GET /my/learning`。

**Rationale**：当前 `/home` 面向访客并由 `HomeService` 缓存分类、站点资料、课程和地图；把学员状态放进去会污染公共缓存并改变匿名契约。`/my/learning` 是课程学习记录列表，不应承担订单、优惠券、消息和地图候选的排序。独立 endpoint 可以在每次进入学习端、刷新或完成学习后重新读取服务端事实，权限边界也清楚。

**Alternatives considered**：

| 方案 | 放弃原因 |
|------|----------|
| 扩展 `/home` | 公开/登录两种缓存语义混在一起，匿名响应无法安全复用 |
| 扩展 `/my/learning` | 需要把商业、消息和地图状态耦合进学习记录接口，返回形状和责任都变重 |
| 前端分别请求多个列表后自行排序 | 违反服务端唯一事实，并会在跨设备/并发更新时产生旧状态决策 |

## R2：下一步计算与稳定排序

**Decision**：`LearningActionService` 在请求内读取现有表，构造候选后一次排序只返回一个主行动。排序由服务端固定，客户端不得重新排序或根据本地进度推断候选。

候选优先级固定为：

1. 支付截止在 24 小时内的有效待支付订单。
2. 使用截止在 24 小时内的适用优惠券。
3. 最近继续中的已授权未完成课节。
4. 有效未读资源消息。
5. 已开始学习地图的下一有效步骤。
6. 收藏后尚未开始的已发布课程。
7. 学习浏览入口。

同一优先级的次序使用与候选含义一致的相关时间：订单/优惠券使用最早截止时间优先；继续学习使用 `course_enrollments.updated_at` 倒序；消息使用消息创建时间倒序；地图使用 `map_enrollments.enrolled_at` 倒序并遵守地图内的阶段/步骤顺序；收藏使用 `favorites.created_at` 倒序。最终以 `resource_type`、资源 ID、课节 ID 等规范化 ASCII 键升序平局。这样“临期”不会因为 FR-004 的“最近时间”字面解释而错误选择更晚截止的资源，同时所有刷新和设备都得到相同结果。

课程继续候选必须同时满足有效课程、有效课节和当前 active entitlement；`last_lesson_id` 无效或已完成时按章节/课节 `sort` 找到下一个有效课节。地图候选沿用 `LearningMapService` 的 `available`、`viewer_authorized`、`completed` 和 `next_step` 语义；没有访问权时目标进入课程详情或获取访问权页面，不因开始地图而授予访问权。

**Alternatives considered**：

| 方案 | 放弃原因 |
|------|----------|
| 加权分数或随机推荐 | 不可审计，也超出首版“不做机器学习推荐”的边界 |
| 只按 `updated_at` 全局排序 | 会让低优先级课程压过支付/优惠券临期事件 |
| 多个主行动并列展示 | 与“只突出一个最值得继续的动作”冲突，增加选择成本 |

## R3：下一步是否持久化

**Decision**：不持久化 `next_action`、候选列表、学习节奏或推荐分数。每次读取都从既有事实重新计算，并返回本次 `generated_at`/`evaluated_at`。

**Rationale**：课程进度、访问权、地图步骤、收藏、订单、优惠券和消息已有各自的权威表与状态机。再建一张“下一步”表会引入失效同步、跨设备覆盖和第二套进度事实。读请求的候选规模受单个学员数据量限制，先用 MySQL 查询和稳定排序满足 2 秒目标；性能不足时优先优化查询与索引，而不是缓存业务状态。

完成课节后仍由现有 `ProgressService` 写入单调进度；客户端收到权威 `LessonProgressDTO` 后立即重新请求 next-action。这样进度写入和下一步读取分成两个清晰事务，不会让视频 heartbeat 每次都重新计算全量下一步。

## R4：提醒节流、每日上限与评估记录

**Decision**：只新增一张 `learner_reminder_evaluations`。它保存每个学员、规则和事件的最新评估状态及最近投递信息，同时通过唯一键承担消息幂等所需的事件身份。

不新增独立的每日计数表：投递成功后用 `last_sent_at` 按上海时区日边界计数，并在准备投递时锁定对应 `accounts` 行，再检查当天已发送数量。这样同一学员的并行评估不会同时看到相同的剩余额度。

不新增 Redis 键、缓存或业务队列。现有 `MessageService` 继续负责 `learner_notifications`、未读计数和可选实时提示；新表只记录业务评估状态，消息内容仍以既有收件箱为事实。

评估状态包括 `not_eligible`、`quiet_hours`、`daily_cap`、`throttled`、`resource_unavailable`、`sent`、`failed`。重复评估更新 `last_evaluated_at`、`evaluation_status` 和 `reason_code`，成功投递保留 `last_sent_at`、`notification_id`、`send_count`，足以解释当前为何发送或未发送。状态表不是完整事件流水；若未来需要运营审计每次扫描，再另立历史审计规格。

事件键规则：

| 规则 | 每次评估选取 | `candidate_key` | 发送上限语义 |
|------|--------------|----------------|--------------|
| 收藏课程待开始 | 最早达到 24 小时且仍未开始的收藏 | `favorite:{favorites.id}` | 同一收藏关系一次；取消后重收藏产生新关系 ID |
| 订单临期 | 截止时间最近的有效待支付订单 | `order:{orders.id}` | 订单状态变化或过期后不再发送 |
| 优惠券临期 | 最早到期且适用的优惠券 | `coupon:{learner_coupons.id}` | 同一评估候选一次；同一课程多张券只选一张 |
| 长期未学习 | 当前无有效学习行为且存在学习目标 | `inactive:{上海本地周起始日}` | 持续未学习每 7 个自然日最多一次 |

每次规则最多产生一个候选，四类候选按“订单、优惠券、收藏、长期未学习”排序；当日已发满 3 条时，未保留候选写入 `daily_cap`，当日不在后续批次补发。`daily_cap` 事件不会被下一轮立即重试，避免低优先级提醒在次日形成补发洪峰；收藏/订单/优惠券本身也会随着事件结束自然失效。

**Alternatives considered**：

| 方案 | 放弃原因 |
|------|----------|
| 三张表分别保存去重、每日计数、评估日志 | 状态跨表更新，事务和清理复杂，首版没有实际收益 |
| Redis 计数器/分布式锁 | 宪章禁止把业务节流状态放入 Redis，重启和恢复也缺少 MySQL 事实 |
| 只依赖 `learner_notifications.idempotency_key` | 能防重复消息，不能解释未命中、勿扰、每日上限和失败重试 |

## R5：消息 kind 与资源跳转

**Decision**：新增一个 `learning_reminder` kind，四类规则放在 payload 的 `rule_code`/`reason_code` 中；不为四条固定规则分别新增 kind。消息资源仍使用既有 `resource_type`/`resource_id`，并将资源类型扩展为 `lesson`、`learning_map`、`order`、`coupon` 及 `course_list`、`map_list`、`coupon_list`、`order_list` 等降级入口。

消息列表响应新增服务端计算的 `resource_path` 和可选 `resource_unavailable_reason`。资源路径只作为已校验的学习端内部路由提示，`resource_available` 每次列表读取时重新检查学员身份、资源状态和访问权；客户端不把保存的 `resource_id` 当作授权证明。

收藏提醒进入课程详情，继续学习进入 `/learn/{courseId}/{lessonId}`，地图进入 `/maps/{id}`，订单进入 `/me/orders/{id}`，优惠券进入 `/me/coupons`，无法锁定具体课程时进入对应列表页。长期未学习提醒的目标从学习候选中重新计算，不能指向订单或已失效目标。

**Alternatives considered**：

| 方案 | 放弃原因 |
|------|----------|
| 四个独立 kind | 前端标签、契约和状态分支增加，但没有新的业务行为 |
| 把完整 URL 只放在 payload | 旧消息与新消息解析不一致，资源可用性无法由服务端统一返回 |
| 让前端按资源 ID 拼接所有路径 | 业务跳转规则分散，容易把已失效或未授权资源显示成可执行 |

## R6：调度频率与失败重试

**Decision**：注册 `learner.reminder.evaluate` scheduled task，默认每 5 分钟运行一次，参数 `batch_size=200`。handler 通过现有 scheduled task runner 扫描 active learner，按账户 ID 分批执行四类规则；同一 scheduled task 继续使用已有的 active-run 防重。

提醒不在登录请求内创建。登录/刷新只读取 next-action；离线学员也可以由定时任务产生站内消息，下次登录从既有消息中心看到。勿扰期间只写评估状态 `quiet_hours`，不调用 `MessageService`，次日 08:00 后的任务重新验证事件并尝试投递。

失败处理：

- 单个候选资源已失效：写 `resource_unavailable`，继续处理同批其他学员，不重试无效目标。
- 消息写入或 MySQL 暂时失败：保留/写 `failed`，让本次任务失败或记录失败上下文；下一次 5 分钟任务用确定性幂等键重试。
- 已经写入消息但更新评估记录失败：下一次重试会命中 `MessageService` 的同一幂等键，不增加消息或未读计数。
- 任务超过下一次触发周期：复用现有 scheduled executor 的 active-run 防重，下一轮跳过并记录 scheduled task run，不并发扫描同一学员。

**Alternatives considered**：

| 方案 | 放弃原因 |
|------|----------|
| 每次登录即时评估并投递 | 学员离线时不会产生提醒，也容易把页面刷新变成通知发送入口 |
| 每秒运行 | 远超四条日历/时间规则的需要，增加数据库扫描噪音 |
| 为失败新建业务重试队列 | 首版引入额外基础设施和 Redis 业务状态，已有定时重试已足够 |

## R7：时间边界与现有订单事实

**Decision**：所有比较在服务端使用 `Asia/Shanghai`。订单截止时间不从客户端传入，也不新增重复的 `expires_at`；由 `OrderService` 统一提供现有 `created_at + 15 分钟` 的 pending 截止计算，超时取消和提醒共用该计算。

订单临期条件为 `status=pending`、当前时间早于截止时间、截止时间不晚于当前时间加 24 小时。由于现行订单生命周期只有 15 分钟，实际上新建 pending 订单就已经处于 24 小时窗口内，提醒文案必须展示准确的 15 分钟截止时间，不能声称“明天到期”。如果产品需要真正的提前一天提醒，应先修改订单生命周期并另行补充订单迁移、支付兼容和回滚设计。

优惠券临期要求实例 `unused`、活动 `active`、当前未过期且至少适用一门已发布收费课程。3 个自然日定义为：当前上海本地日开始时刻至第 4 个本地日开始时刻之前，且 `expires_at` 仍晚于当前时刻；例如 9 月 4 日当天会覆盖 9 月 4 日至 9 月 7 日结束前到期的券。具体适用范围和满减门槛复用 `CouponService` 的现有匹配逻辑。

长期未学习使用服务端产生的有效 `lesson_progresses` 行的最近 `updated_at`；登录、列表浏览、课程详情浏览和仅有收藏不算有效学习。连续 7 个自然日以最近有效学习时间与当前上海本地日边界计算，存在至少一个可执行学习目标时才创建提醒。

勿扰边界为本地时间 `22:00 <= time < 08:00`。规则评估仍可在该时段运行，但不创建未读消息、不触发 Push；08:00 后按优先级和当天已发送计数逐条发送，超过 3 条直接标记 `daily_cap`。

## R8：降级、安全和前端一致性

**Decision**：每个依赖单独失败都进入服务端 `degraded` 结果，保留已成功读取的候选；全部候选依赖失败时不猜测课程或进度，只返回明确的浏览入口或空状态。前端只渲染 endpoint 的 `action`、`state`、`reason` 和 `target.path`。

资源打开仍走原有路由和 controller 的鉴权/所有权检查。订单必须带当前学员 ID，优惠券必须带当前学员 ID，课节必须再次验证课程访问权和课节启用状态；下架课程、归档课节、取消收藏、订单已支付/已取消、优惠券已用/已过期都只能得到不可用说明或服务端给出的降级入口。

完成课节的流程为：`ProgressService` 在数据库事务内维持完成单调性和课程汇总，客户端只接受其响应；当响应表明结果已生效时，立即调用 `GET /me/next-action`。旧页面不回写本地课程进度，也没有客户端缓存可以覆盖新结果。消息已读与学习结果各走自己的既有规则，不在 next-action 服务中伪造。

**Alternatives considered**：

| 方案 | 放弃原因 |
|------|----------|
| API 异常时用本地 `myLearning` 猜下一步 | 可能展示已撤销访问权、已完成课节或过期支付入口 |
| 将下一步保存在 Pinia 并跨页面当缓存 | 会形成前端学习状态副本，跨设备和刷新无法保证一致 |
| 资源可用性只在生成时判断 | 生成与点击之间存在下架、支付和授权变化窗口 |

以上决策已消除 Technical Context 中的未知项，无 `[NEEDS CLARIFICATION]`。
